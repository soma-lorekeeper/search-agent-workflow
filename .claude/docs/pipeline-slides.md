# 파이프라인 소개 슬라이드 구성안

> pipeline-components.md 기반. 총 6장 구성 — 전체 개요 1장 + 구성 요소별 1장 + 탐지 정확도 실험 2장.
> 각 슬라이드마다 (1) 소제목, (2) 슬라이드 생성 프롬프트에 넣을 내용, (3) 생성 이미지 배치 위치를 명시한다.

---

## Slide 1. 전체 개요

**소제목**: Lorekeeper AI 구성 요소 — 인덱싱 · 검색 · 탐지

**슬라이드에 들어갈 내용**:
- Lorekeeper AI는 두 개의 파이프라인과 하나의 검색 도구 계층으로 구성된다.
  1. **Indexing Pipeline** — 회차 원고를 지식 그래프로 쌓는다
  2. **Retrieval Tools** — 쌓인 그래프를 조회하는 검색 도구 3종 (파이프라인이 아니라, 두 파이프라인 사이를 잇는 조회 계층)
  3. **Detecting Pipeline** — 새 회차가 기존 설정과 어긋나는지 검사한다
- 관계: Indexing이 만든 지식 그래프를 Retrieval Tools가 조회하고, Detecting이 이 도구들을 이용해 신규 회차를 검증한다.
- 한 줄 요약: "회차를 쌓고(Indexing) → 꺼내 보고(Retrieval) → 어긋남을 잡는다(Detecting)"

**이미지 위치**: 슬라이드 하단 2/3 영역, 가로로 넓게.
**이미지 프롬프트(예시)**: "세 개의 박스가 순환 구조로 연결된 심플한 시스템 다이어그램. 왼쪽 박스 'Indexing'은 문서 아이콘에서 그래프 아이콘으로 향하는 화살표, 가운데 'Knowledge Graph'는 노드-엣지 네트워크, 오른쪽 'Detecting'은 돋보기와 경고 아이콘. 'Retrieval'은 그래프와 Detecting 사이를 잇는 양방향 화살표 위에 표시. 플랫 디자인, 흰 배경, 파란색 계열."

---

## Slide 2. Indexing Pipeline

**소제목**: Indexing Pipeline — 회차 원고를 지식 그래프로

**슬라이드에 들어갈 내용**:
- 역할: 새 회차 원고를 받아, 이전 회차까지 누적된 지식 그래프 위에 이번 회차의 내용을 얹는다.
- 산출물은 두 레이어다:
  - **추출 KG** — 인물·장소·사건·조직·아이템과 인물 상태를 그래프 노드로 추출
  - **근거 레이어** — 원고를 문장 단위 조각(Chunk)으로 저장·임베딩. 추출된 모든 사실이 원문 조각을 근거로 가리킨다
- 구성 모듈 (처리 순서대로):
  | 모듈 | 담당 |
  |---|---|
  | 배경 컨텍스트 조립 | "지금까지의 이야기"(전역 요약 + 최근 회차 요약 + 그래프 덤프)를 준비 |
  | Splitter / Chunk 레이어 | 원고를 문장 단위로 잘라 근거 조각으로 저장·임베딩 |
  | LLM 추출 | 원고에서 인물·사건·상태를 스키마에 맞게 추출 |
  | Resolver | 회차마다 새로 생기는 중복 노드를 기존 그래프와 병합 |
  | KG-Chunk 연결 | 추출된 사실을 근거 원문 조각과 링크 |
  | 요약 계층 갱신 | 회차 요약과 전역 줄거리 요약을 갱신해 다음 회차 준비 |

**이미지 위치**: 슬라이드 우측 절반 (좌측에 텍스트·표, 우측에 이미지). 또는 표를 줄이고 상단 텍스트 + 하단 전체 폭 플로우 이미지.
**이미지 프롬프트(예시)**: "왼쪽에서 오른쪽으로 흐르는 6단계 파이프라인 다이어그램. 시작은 소설 원고 문서 아이콘, 끝은 노드-엣지 지식 그래프 아이콘. 중간 단계는 '컨텍스트', '청킹', 'LLM 추출', '병합', '근거 연결', '요약'을 나타내는 작은 아이콘 박스들. 플랫 디자인, 흰 배경, 파란색 계열."

## Slide 3. Retrieval Tools

**소제목**: Retrieval Tools — 그래프를 조회하는 3가지 검색 도구

**슬라이드에 들어갈 내용**:
- 역할: 인덱싱으로 쌓인 지식 그래프를 조회한다. 세 도구는 **서로 다른 층위**를 검색한다.
  | 도구 | 검색 대상 | 이런 질의에 강함 |
  |---|---|---|
  | hybrid_search | 원문 조각 (Chunk) | 표기·숫자·고유명 — "그 표현이 원문에 있나" |
  | fact_search | 추출된 사실 (사건·인물 상태) | "누가 X를 했나" — 사실·규칙 조회 |
  | entity_search | 엔티티 (인물·아이템·조직·장소) | 특정 대상의 속성과 상태 이력 |
- 공통 특성 (간단히 한 줄씩):
  - 벡터 검색 + 풀텍스트 검색을 함께 쓰는 하이브리드 방식 (hybrid/fact)
  - 작품 단위 격리 — 다른 작품의 내용은 검색되지 않는다
  - LLM 에이전트가 직접 호출할 수 있는 도구 형태로 노출된다

**이미지 위치**: 슬라이드 상단 우측 또는 표 아래 하단 전체 폭.
**이미지 프롬프트(예시)**: "하나의 지식 그래프(노드-엣지 네트워크)를 향해 세 개의 돋보기가 각기 다른 층을 들여다보는 다이어그램. 그래프는 3개 층(원문 문서 층, 사실 카드 층, 인물 프로필 층)으로 쌓인 형태. 각 돋보기에 라벨 'hybrid', 'fact', 'entity'. 플랫 디자인, 흰 배경, 파란색 계열."

## Slide 4. Detecting Pipeline

**소제목**: Detecting Pipeline — 신규 회차의 설정 오류 탐지

**슬라이드에 들어갈 내용**:
- 역할: 새 회차 원고가 직전 회차까지의 설정(지식 그래프)과 어긋나는 지점을 찾아낸다.
- 구성 모듈 (처리 순서대로):
  | 모듈 | 담당 |
  |---|---|
  | Extract | 원고에서 검증 대상 주장(claim)을 구조화해 뽑는다 |
  | Routing / Retrieve | claim마다 검색 질의를 만들어 Retrieval 도구로 근거를 수집 |
  | Docstore | 수집된 근거를 하나의 문서고로 병합·중복 제거 |
  | Judge | claim들을 문서고와 대조해 설정 오류를 판정 |
  | Findings | 오류로 확정된 claim만 원문 인용·근거 위치·판정 사유와 함께 기록 |
- 흐름 한 줄 요약: "주장을 뽑고 → 근거를 모아 → 대조 판정한다"
- Retrieval Tools(앞 슬라이드)가 이 파이프라인의 근거 수집 단계에서 쓰인다는 연결 언급.

**이미지 위치**: 슬라이드 하단 전체 폭 (상단에 표, 하단에 플로우 이미지). 또는 우측 절반.
**이미지 프롬프트(예시)**: "왼쪽에서 오른쪽으로 흐르는 5단계 파이프라인 다이어그램. 시작은 새 원고 문서 아이콘, 끝은 경고 표시가 붙은 리포트 아이콘. 중간 단계는 '주장 추출'(말풍선 카드), '근거 검색'(돋보기+그래프), '문서고'(서류함), '판정'(저울) 아이콘 박스. 플랫 디자인, 흰 배경, 파란색 계열."

## Slide 5. 탐지 정확도 실험 — 벤치마크 설계

> 근거 데이터: `data/ch6_test_draft_errors.md`(테스트 케이스 설계)

**소제목**: 탐지 정확도 실험 — 난이도 사다리 벤치마크

**슬라이드에 들어갈 내용**:
- 실제 웹소설 1~5화를 인덱싱한 상태에서, 6화 초고를 5개 버전으로 재작성하고 **버전마다 설정 오류 5개씩(총 25개)을 의도적으로 심었다**.
- v1 → v5로 갈수록 탐지에 더 많은 추론이 필요하도록 **난이도 사다리**로 설계:
  | 단계 | 오류 유형 | 예시 |
  |---|---|---|
  | v1 | 명시적 모순 — 확립된 사실과 정면 충돌 | 살아있는 인물을 죽었다고 서술 |
  | v2 | 속성값 오류 — 속성 하나만 틀림 | 보상 300코인 → 500코인 |
  | v3 | 미세 표면 오류 — 한두 글자·숫자 차이 | 채널 #BI-7623 → #BI-7263 |
  | v4 | 앵커 소실 — 주어가 대명사, 고유명사 없음 | "그 여자도 나와 같은 계약직" |
  | v5 | 추론 필요 — 여러 서술을 결합해야 모순 판명 | 던져 버린 물건이 다시 손에 있음 |
- 오탐 측정: 오류를 심지 않은 **실제 6화 원고(clean)** 를 별도 케이스로 두어, 정상 원고에서 억울한 경보가 나오는지 함께 측정한다.
- 기대 성질: v1 → v5로 갈수록 검출이 어려워야 한다 — 그렇지 않으면 난이도가 아닌 다른 축의 결함이 있다는 신호.

## Slide 6. 탐지 정확도 실험 — 결과와 개선

> 근거 데이터: `data/eval_claims/report_judge_whole-bc_p1.md`(초기),
> `report_judge_line-3000-qav2_p4-n3.md`(최종), `report_judge_line-3000-qav2_p4-n3_c6.md`(clean 6화 오탐 검사)

**소제목**: 탐지 정확도 실험 — 68%에서 84%로

**슬라이드에 들어갈 내용**:

**초기 실험 결과**
- 검출 **17/25 (68%)** — v1~v4 각 4/5, v5 1/5.
- 문제: 가장 쉬운 v1조차 놓쳤고, 실패는 대부분 근거를 찾고도 "확인되지 않는다"로 판정을 회피하거나, 대조할 축을 잘못 짚는 패턴.

**개선 내용 (3개 축, 한 줄씩)**
- **claim 추출 재설계** — 주장을 quote/axis(대조축)/value(값) 구조로 뽑도록 스키마를 바꾸고, 원고에 줄 번호를 매겨 조각 단위로 병렬 추출.
- **검색 라우팅 고정** — 질의 생성을 LLM이 아닌 코드 규칙으로: axis 단독 + axis·value 결합 두 계열 × 원문/사실 2채널. 같은 입력이면 항상 같은 검색 → 개선 효과를 정확히 측정 가능.
- **판정 프롬프트 반복 개정 (p1→p4)** — 실패 사례를 역추적해 원인별로 수정: 사건의 순서로 생사·이동의 선후를 따지게, "확인 불가" 회피를 차단, 정상적인 값 변화(레벨업)와 되돌릴 수 없는 상태의 역행(버린 물건 재등장)을 구분. 판정 안정화를 위해 표본 3개의 중앙값 사용.
- 실험 방법: 한 번에 한 변수만 바꾸고 매 구성마다 25건 전체 재실행.

**개선 후 실험 결과**
- 검출 **21/25 (84%)** — v1~v4 **완전 검출(20/20)**, v5 1/5.
- 오탐 검사: clean 6화 원고에서 추출된 claim 175개 전부가 운영 임계값 미만 — **오탐 경보 0건**.
- 남은 한계: v5(여러 문장을 결합해야 하는 추론형)는 여전히 1/5 — 문장 단위로 근거를 찾는 현 구조의 한계로, 향후 과제.

**차트 위치**: 하단 전체 폭 — before/after 막대 차트(v1~v5별 검출 수, 초기 vs 개선 후 2색 막대. 옆에 clean 6화 오탐 0건 표기). **수치 차트는 생성 이미지가 아니라 실제 차트로 그린다**(생성 이미지는 숫자를 왜곡한다).

**차트 데이터** (검출 수 / 각 5건 만점):

| 구성 | v1 | v2 | v3 | v4 | v5 | 합계 |
|---|---|---|---|---|---|---|
| 초기 | 4 | 4 | 4 | 4 | 1 | 17/25 (68%) |
| 개선 후 | 5 | 5 | 5 | 5 | 1 | 21/25 (84%) |

clean 6화 오탐: claim 175개 검사 → 경보 **0건** (차트 우측에 별도 표기)
